### AI purpose-level context

The provider is selected centrally; the backend does not make a separate provider choice per endpoint. Supported purposes include resume profile/analysis, interview first question/follow-up/evaluation/report, scenario evaluation, and STAR evaluation. Inputs are assembled server-side from the relevant user-owned source and the current request. Interview report generation uses the answered interview transcript; interview answer evaluation receives the submitted answer and question context. The Vietnamese-only output instruction is enforced in Business AI operations. No provider API key is returned to clients.

Provider processing and retention occur outside this repository and cannot be inferred from adapter code. Production model/provider configuration must be checked in the deployment secret/configuration system without printing secret values.

## Account deletion as implemented

Authenticated deletion and verified external deletion converge on `IPrivacyService.RequestDeletionAsync`. Acceptance records a queued deletion request and immediately revokes active refresh-token sessions; it does not promise a grace period. The API/worker polling process deletes user data asynchronously. There is no cancellation route and no `scheduledHardDeleteAt` contract.

The worker removes associated R2/local objects for stored files, upload intents, and the avatar before removing database records. If an upload intent still has an unexpired signed PUT capability, the deletion job is deferred until the latest capability expires so a late upload cannot recreate an object after cleanup. Transient deletion errors are retried; after three failed attempts the request is marked failed. Consequently, completion is not guaranteed after persistent provider failure and a failed job requires operational follow-up.

After object cleanup, the canonical database transaction explicitly removes owner-scoped private domain data, including ScenarioAttempt answers/evaluations and StarAttempt questions/answers/evaluations, and personal outbox jobs whose aggregate IDs are those attempts. Generic owner cleanup also removes their realtime notifications, idempotency records, and reporter-owned ContentReports. Outstanding practice reservations are voided through the existing feature-entitlement service; previously consumed/voided reservations and immutable billing/usage ledgers remain unchanged. The account is anonymized and the privacy request marked completed in the same transaction.

On PostgreSQL, Scenario/STAR worker persistence and the purge lock the same user row. Workers re-read attempt/job existence and deletion state before AI and again before persisting success or failure, without holding that lock during AI. An in-flight provider request may finish after deletion, but its result cannot recreate backend attempt data or notifications. `PrivacyPracticeDeletionTests` covers owner isolation, retained ledgers, worker-first cleanup, and coordinated deletion during successful/failing AI calls on PostgreSQL. This does not establish erasure of copies already sent to external providers.

Resume soft-delete is a distinct flow: it hides the resume and schedules object deletion with bounded exponential backoff, but it does not immediately erase resume database metadata. No general scheduled orphan-object scan or expiry purge for upload intents was found. An unfinalized upload object can therefore outlive its intent expiry until account deletion or provider-side/manual cleanup; the retention period is **UNVERIFIED**.

## Verified gaps and decisions still needed

1. No generic cleanup job for expired upload intents/orphan objects was found. Account deletion and resume soft-delete have cleanup paths, but abandoned upload objects may persist.
2. Orders, payment/usage ledgers, deletion-request records, and Sentry/hosting logs outlive account deletion in the code. Their retention purpose and duration are not defined here and need owner/privacy/legal confirmation; no legal basis is invented.
3. ContentReports submitted by a user are currently deleted with that reporter's data. This removes moderation history; whether a minimized/anonymized moderation record should instead be retained is unresolved. Scenario/STAR report creation requires ownership; admin moderation operates on that report's stored snapshot, not a separate cross-owner report-creation path.
4. Runtime values for provider selection, DSNs, hosting/database/storage accounts, regions, and external retention settings must be checked by an authorized operator in each provider dashboard/configuration store. Do not paste secrets into this document or logs.
